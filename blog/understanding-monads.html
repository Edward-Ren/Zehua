1. Monad：从函数组合的问题开始

普通函数的组合只需要让输出和输入的类型接上：

f :: a -> b
g :: b -> c

g . f :: a -> c
-- (g . f) x = g (f x)

g . f 表示先执行 f，再执行 g。例如先加一、再乘二，((* 2) . (+ 1)) 3 得到 8。但如果一个计算除了产生结果，还可能失败、记录日志，或者改变传递中的状态，类型就变了：

f :: a -> m b
g :: b -> m c

这里 m 是类型构造器，m a 是带有某种计算上下文的结果类型。它不一定是实际装着一个 a 的容器：Maybe a 可能没有结果，IO a 则描述一个执行后可产生 a 的输入输出计算。现在 f 返回 m b，g 却需要 b，普通的 g . f 因此不能直接使用。

Monad 提供一种满足规律的组合方式，把这些带上下文的计算接起来。不同实例决定组合时如何处理上下文：Maybe 传播可能的失败，List 考虑多个可能结果，Writer 累积日志，State 传递状态，IO 顺序组织输入输出计算。它们的共同点是 composition，而不是某一种特定的副作用。

这也接上了第一篇的 error propagation 问题：业务函数可以专注于自己的一步，组合规则负责把额外结构贯穿整个计算。接下来先明确，这种“组合”发生在哪个 category 里。

2. Kleisli Category 从哪里来？

一个 category 有 objects、objects 之间的 morphisms、每个 object 上的 identity，以及可首尾连接的 morphisms 的 composition。以 Set 为例，objects 是集合，morphisms 是函数，identity 是 id x = x，composition 就是普通函数组合。它们满足：

idB∘f=f=f∘idA
h∘(g∘f)=(h∘g)∘f

第一条说 identity 不改变箭头，第二条说改变组合的括号不改变结果。这里 f 从 A 到 B，g 从 B 到 C，h 从 C 到 D。Haskell 类型和函数可以帮助理解这些结构；下面的数学定义则是在给定的范畴 𝒞 中陈述。

固定一个 Monad M 后，f :: a -> m b 可以有两种看法。在原范畴 𝒞 中，它是 A → MB 的态射；在新建的 Kleisli category 𝒦 中，同一个 f 被视为 A → B 的态射。这不是把 MB 当成 B，而是重新定义了两个 objects 之间允许的箭头：

𝒦(A,B)=𝒞(A,MB)

因此 𝒦 和 𝒞 有相同的 objects，却有不同的 morphisms 和 composition。若 f、g 的类型如上一节，Kleisli composition 写作：

import Control.Monad ((>=>))

-- f :: a -> m b, g :: b -> m c
-- Under the constraint Monad m:
f >=> g :: a -> m c

>=> 也叫 Fish，按从左到右的顺序读：先 f，再 g。Kleisli identity 是 pure :: Monad m => a -> m a；它只引入一个值，不加入额外的计算效果。例如在 Maybe 中 identity 是 Just，在 Writer 中它附带空日志。

关系的方向很重要：从一个 Monad 出发，才能用它的 unit 和 composition 构造 Kleisli category。Monad Laws 保证这里的 identity 和 composition 满足 Category Laws。仅有一个 endofunctor，还没有指定怎样从嵌套结果回到一层，也没有这些规律，不能自动得到所需的 Kleisli category。第 9 节会把这件事写成数学公式；先看 Haskell 中具体怎样连接计算。

3. Monad 的五个核心操作

下面列出操作的完整约束。现代 Haskell 中 Monad 以 Applicative 为 superclass，而 Applicative 又要求 Functor；所以 Monad 也能使用 pure 和 fmap。pure 本身只需要 Applicative，并非 Monad 独有。签名是接口说明，后面的表达式可以在 GHCi 中求值。

import Control.Monad ((>=>), join)

pure   :: Applicative m => a -> m a
return :: Monad m => a -> m a
(>=>)  :: Monad m => (a -> m b) -> (b -> m c) -> a -> m c
(>>=)  :: Monad m => m a -> (a -> m b) -> m b
join   :: Monad m => m (m a) -> m a
(>>)   :: Monad m => m a -> m b -> m b

pure / return：引入一个值

pure 5 :: Maybe Int 得到 Just 5。在 Monad 中 return 与 pure 的角色相同；本文统一使用 pure。它不负责提前结束函数。

Fish 与 Bind：两种不同的连接位置

Fish 的两边都是函数，得到的仍是函数；Bind 左边则已经是一个 monadic value，右边是接收普通结果的下一步计算：

-- Fish expressed using Bind:
f >=> g = \x -> f x >>= g

Just 10 >>= (\x -> Just (x * 2))
-- Just 20

((\x -> Just (x + 1)) >=> (\y -> Just (y * 2))) 3
-- Just 8

最后一行先把两个函数组合，再给这个新函数输入 3。Bind 的例子则从现有的 Just 10 开始。\x -> ... 是匿名函数；符号不熟悉时可以查看文末的语法速查。

join：合并两层相同的上下文

join (Just (Just 5))
-- Just 5

join (Just Nothing) :: Maybe Int
-- Nothing

join 的输入必须具有 m (m a) 的形状。如何合并由实例决定，并不是任意删除一层包装。下一节会解释为什么它正好补上 fmap 所缺少的一步。

>>：忽略值，保留计算效果

m >> k = m >>= (\_ -> k)

Just 3 >> Just 8
-- Just 8

Nothing >> Just 8
-- Nothing

匿名函数 \_ -> k 接收一个参数但不用它。忽略返回值不等于忽略前一步计算：第二个例子仍然传播失败，根本不会进入后续成功分支。对 Writer 而言，前一步的日志也仍会保留。

4. Functor、Bind 与 Join：先看清类型

我最容易混淆的是：对一个返回 Maybe 的函数使用 fmap，结果究竟有几层 Maybe？把类型代进去就能看出来：

fmap :: Functor m => (a -> b) -> m a -> m b

ma :: Maybe Int
ma = Just 5

f :: Int -> Maybe Bool
f x = Just (x > 0)

ma 是值的名字；m a 才是类型构造器 m 应用于类型 a。这里 fmap 签名里的 b 被替换成 Maybe Bool，而外层 m 是 Maybe，所以：

fmap f ma :: Maybe (Maybe Bool)
-- Just (Just True)

ma >>= f :: Maybe Bool
-- Just True

join (fmap f ma) :: Maybe Bool
-- Just True

fmap 保留外层结构，再对其中的值应用 f；新的一层来自 f 自己返回 Maybe。并不是每次 fmap 都产生嵌套：fmap (> 0) ma 只有 Maybe Bool 一层，因为 (> 0) 返回普通 Bool。

Bind 则把下一步返回的上下文与现有上下文合并。因此，对于同一个 lawful Monad，有：

ma >>= f = join (fmap f ma)

join mma = mma >>= id

fmap f ma = ma >>= (\a -> pure (f a))

这些是操作之间的等式，不是在文件中重新声明库函数。第一条先 map 再 flatten；第二条把内部计算交给 id；第三条说明可以用 Bind 和 pure 得到与 Monad 兼容的 fmap。在当前 f 返回 Maybe 的例子里，第三条的 pure 仍会引入外层 Maybe，所以结果仍是 Maybe (Maybe Bool)。

相反，join (Just (5 :: Int)) 是类型错误：join 需要 Maybe (Maybe a)，拿到的却是 Maybe Int。笔记中的 join (Just 5) 在这些标准实例下同样不能通过类型检查；数字 5 不是内层 Maybe。显式写出 Int，可以把这个类型错位看得更清楚。

5. Maybe：让失败沿着计算传播

定义一个只允许偶数除以二的函数。除不尽就没有结果：

half :: Int -> Maybe Int
half x =
  if even x
  then Just (x `div` 2)
  else Nothing

Maybe 的 Bind 可以用两条规则理解：

Just x  >>= f = f x
Nothing >>= f = Nothing

有结果时，把 x 交给下一步；没有结果时，直接保留 Nothing。这两行是实例行为的说明，不是需要额外复制的 instance 声明。于是：

Just 24 >>= half >>= half >>= half
-- Just 3

Just 10 >>= half >>= half
-- Nothing

成功的路径是 24 → 12 → 6 → 3。每次传给 half 的输入都为偶数；最后的 3 虽然是奇数，却是合法输出，因为我们没有再对它调用 half。失败的路径则先得到 Just 5，第二次 half 接收到 5，返回 Nothing。继续接任何同类型的下一步，Bind 都会传播这个失败。

Maybe 允许计算失败，不代表每个计算都会失败。我们仍要在 half 中判断它自己的失败条件，但不用在每两个步骤之间反复检查上一项是否成功。也可以定义 half >=> half，得到一个可以重复使用的 Int -> Maybe Int 函数。

6. Writer：结果与日志一起组合

另一个例子不需要失败，而需要同时保留结果和过程记录。可以把 Writer w a 理解为一对 (a, w)：a 是计算结果，w 是累积的日志。实际库使用封装类型，通过 runWriter 取出这对值。下面代码使用 mtl 包的 Control.Monad.Writer.Strict，不是只有 base 的程序：

import Control.Monad.Writer.Strict
  (Writer, writer, runWriter, tell)

addOne :: Int -> Writer String Int
addOne x = writer (x + 1, "addOne; ")

double :: Int -> Writer String Int
double x = writer (x * 2, "double; ")

-- Evaluate in GHCi:
runWriter (addOne 3 >>= double)
-- (8, "addOne; double; ")

addOne 把 3 变成 4，并留下第一段日志；Bind 将 4 传给 double，得到 8 和第二段日志。它返回新的数值结果，同时按先后顺序合并两段日志。日志是返回的数据，这里并没有向终端打印信息。

下面的等式是解释 Writer 行为的伪代码，左侧的 pair 不是库中的 Writer 构造器：

pure a             ≈ (a, mempty)
(a, w1) >>= f      ≈ let (b, w2) = f a
                       in (b, w1 <> w2)

符号 <> 是日志的组合操作；在 Monoid 上也可以写成 mappend。Writer 的 Monad instance 要求 Monoid w，因为 pure 需要空日志 mempty，Bind 需要合并日志，而且这些操作必须满足：

mempty <> w = w
w <> mempty = w
(u <> v) <> w = u <> (v <> w)

前两条是 identity，第三条是 associativity。空日志不影响已有记录，改变组合的括号也不改变最终日志；这些正好支持 Writer 的 Monad Laws。字符串的 mempty 是 ""，组合操作就是 ++。Monoid 不要求交换律：

"F;" ++ "G;" /= "G;" ++ "F;"
-- True

先 F 后 G 和先 G 后 F 的记录不同。Associativity 允许重新分组，不允许交换执行顺序。

如果只想追加一段日志，可以使用 tell。专门化到 Writer 后，它的类型为 tell :: Monoid w => w -> Writer w ()。() 是 unit value，表示没有需要继续使用的数值结果；日志仍然存在：

runWriter (tell "start; " >> addOne 3 >>= double)
-- (8, "start; addOne; double; ")

这里 >> 忽略 tell 返回的 ()，却保留了 "start; "。同一个 sequencing 接口，在 Maybe 中负责失败传播，在 Writer 中负责日志累积。

7. do Notation：把 Bind 写得更直观

当后一步依赖前一步的值，连续的 Lambda 会让表达式显得拥挤。普通的 monadic do notation 把这些 Bind 写成逐行形式：

result :: Maybe Int
result = do
  x <- Just 8
  y <- Just (x + 3)
  pure (y * 2)
-- Just 22

在这个只使用变量绑定的例子中，等价的 Bind 表达式是：

result :: Maybe Int
result =
  Just 8 >>= \x ->
  Just (x + 3) >>= \y ->
  pure (y * 2)

第一步把 8 交给后续函数，所以 x 是 Int，而 Just 8 是 Maybe Int。第二步得到 Just 11，把 11 绑定给 y；最后 y * 2 是普通 Int 22，pure 在当前 Maybe 上下文中返回 Just 22。

<- 表示把计算产生的值绑定到后续代码的名字上，具体传递仍由 >>= 完成；它不是一个可以在任意位置把 Maybe 拆开的操作。没有 <- 的中间计算语句通常使用 >>，忽略其结果并保留效果。如果某一步变成 Nothing，后续计算仍会被跳过。

do 没有消除 Monad，只是隐藏了显式的 Bind 与 Lambda。把最后的 pure 改成 return，也不表示“提前退出”：Haskell 的 return 是产生一个 monadic value 的函数，不是命令式语言的控制流语句。

8. Monad Laws：组合为什么可靠？

只有类型签名还不够：自定义的操作即使能通过类型检查，也未必遵守预期的组合规则。Lawful Monad 还必须满足以下等式。

-- Left identity
pure x >>= f = f x

-- Right identity
m >>= pure = m

-- Associativity
(m >>= f) >>= g =
  m >>= (\x -> f x >>= g)

Left identity 表示把普通值引入上下文后再交给 f，与直接调用 f 一样。例如 pure 8 >>= half 和 half 8 都是 Just 4。Right identity 表示把已有计算的结果交给 pure，不会增加新的效果。

(Just 5 >>= pure) :: Maybe Int
-- Just 5

pure (Just 5) :: Maybe (Maybe Int)
-- Just (Just 5)

这里特意给第二行的外层 pure 指定 Maybe，否则 pure 的上下文还没有确定。两者不同的原因是：Bind 交给 pure 的是 5；直接 pure (Just 5) 交给 pure 的却是整个 Just 5。Right identity 并没有说“直接再包一层也不变”。

Associativity 表示先把前两步接起来，或者先组织好后两步再接入，得到相同的计算。执行顺序仍然是 m、f、g。Writer 的例子里两种括号得到相同的日志，而不是允许日志倒序。

把这些规律改写成 Fish 的形式，就直接看到了 Kleisli category 的 Category Laws：

pure >=> f = f
f >=> pure = f

(f >=> g) >=> h =
  f >=> (g >=> h)

pure 是这套 composition 的 identity，>=> 满足 associativity。第 2 节所说的“Monad 提供一个 category 所需的结构”，具体就是这件事。

9. 数学定义：Endofunctor、Unit 与 Multiplication

回到范畴论，一个 Monad 是三元组 (T, η, μ)。这里把前面的 M 改记为常见的 T：

T:𝒞→𝒞,η:Id𝒞⇒T,μ:T2⇒T

T 是 endofunctor：把对象 A 送到 TA，并把态射 f 送到 T(f)，保留 identity 和 composition。η 和 μ 是 natural transformations。η 的分量 η_A : A → TA 对应 pure；μ 的分量 μ_A : T(TA) → TA 对应 join。这里 T² 表示函子复合 T ∘ T，不是数字平方。Natural transformation 要求这些分量与态射的映射相容，而不是对每个对象随意挑一个函数。

除了 naturality，η 与 μ 还必须满足下面两张交换图。每条从同一起点到同一终点的路径，都表示同一个 natural transformation。

μ∘Tμ=μ∘μT

更精确地，在对象 A 处，这是：

μA∘T(μA)=μA∘μTA

Tμ 的分量 T(μ_A) 对应 fmap join，先在外层中合并内部两层；μT 的分量 μ_TA 对应先用 join 合并外部两层。之后再 join 一次，结果相同。这是“改变分组不改变结果”的 flattening 版本。

μ∘ηT=idT=μ∘Tη

顶边 ηT 在 A 处是 η_TA，把整个 TA 用 pure 引入一层；左边 Tη 是 T(η_A)，对应在 TA 内部 fmap pure。然后应用 μ_A，都得到 TA 上的恒等映射。因此，对任意 monadic value ma，join (pure ma) = ma，且 join (fmap pure ma) = ma。

现在可以写出 Kleisli composition。对原范畴中的 f : A → TB、g : B → TC，定义：

g⋆f=μC∘T(g)∘f

从右往左读：f 先产生 TB；T(g) 把 g 映入上下文，得到 T(TC)；μ_C 再把两层合为 TC。对应 Haskell，就是 (f >=> g) x = join (fmap g (f x))。Kleisli identity 则由 η 给出。因而 pure、join 与 Functor 的表示，以及 pure、Bind 或 Fish 的表示，在满足相应规律与相容性条件时，描述的是同一个 Monad 结构。

10. 从 Monad 走向 Arrow

到这里，Monad 的核心可以连成一条线：pure 引入值，Bind 把一个计算交给下一步，join 合并嵌套上下文，而 Fish 直接组合 Kleisli 函数。Monad Laws 使这些连接构成 Kleisli category。Maybe 和 Writer 展示了同一种结构如何保留不同的计算含义。

接下来学习 Arrow，仍然从 composition 出发。f >=> g 组合返回 monadic value 的函数；f >>> g 则是更一般的、从左到右的 Category composition：

结构Kleisli 函数一般 Arrow
表示a -> m barr a b
组合>=>>>>，来自 Category
IdentitypureControl.Category.id，也可写 arr Prelude.id
提升普通函数 fpure . farr f
作用于 pair 的第一项对第一项计算并保留第二项first
arr :: Arrow arr => (a -> b) -> arr a b
first :: Arrow arr => arr a b -> arr (a, c) (b, c)

签名中左侧的 arr 是函数名，类型中的 arr 是有两个类型参数的构造器。arr 提升一个普通函数，first 则让已有计算只作用于 pair 的第一项，同时把第二项传下去。这与之前学习的 products 有直接联系。

对于 lawful Monad m，Haskell 的 Kleisli m 把 a -> m b 包成 Kleisli m a b，并提供 Arrow instance。继续使用第 5 节的 half：

import Control.Arrow (Kleisli(..), arr, first, (>>>))

quarter :: Kleisli Maybe Int Int
quarter = Kleisli half >>> Kleisli half

runKleisli quarter 24
-- Just 6

runKleisli (first (Kleisli half)) (8, "keep")
-- Just (4, "keep")

runKleisli (arr (+ 1) :: Kleisli Maybe Int Int) 3
-- Just 4

这里 Kleisli f >>> Kleisli g 正好对应 Kleisli (f >=> g)。但一般的 Arrow 接口并不要求所有实例都由 Monad 导出。还要区分 pure 与 arr：pure 把一个值引入 monadic context，arr 把一个函数提升成 Arrow；在 Kleisli 实例中，arr f = Kleisli (pure . f)。

下一步的问题于是变为：除了串行组合，怎样用 arr 和 first 组织输入输出的结构？这就是从 Monad 走向 Arrow 时，要继续追踪的主线。
